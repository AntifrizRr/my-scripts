# Кейс автоматизации интеграционных и операционных процессов

Репозиторий содержит обезличенные примеры автоматизации, подготовленные на основе реальной операционной логики. Проект показывает, как ручные процессы вокруг Google Sheets, Slack-уведомлений, API-обновлений и сверки данных можно превратить в более управляемую и повторяемую автоматизацию.

## Что автоматизируется

- обработка изменений статусов в операционной Google-таблице;
- отправка Slack-уведомлений при выполнении заданных условий;
- перенос подтвержденных записей между Google Sheets;
- синхронизация справочных и отчетных данных;
- обновление названий партнеров через API партнерской платформы;
- повторная проверка результата после API-обновления;
- сохранение статусов обработки для повторных запусков;
- базовое логирование и обработка частичных ошибок.

## Стек

- Google Apps Script / JavaScript;
- Python;

- HTTP API;
- pytest;
- Ruff;
- GitHub Actions;
- простой secret scan для проверки публичного репозитория перед публикацией.

## Структура проекта

- `google-apps-script/aff-partners-info` — логика Google Apps Script: обработка событий в таблицах, уведомления, синхронизация данных и технические логи;
- `rename_partners` — Python-скрипты для API-обновлений, проверки результата и последующей синхронизации с Google Sheets;
- `docs/architecture.md` — краткое описание архитектуры и потока данных;
- `.github/workflows/checks.yml` — автоматические проверки кода, тестов и возможных секретов.

## Общая логика процесса

1. Пользователь меняет статус или данные в операционной Google-таблице.
2. Apps Script проверяет измененную строку, обязательные поля и условия обработки.
3. При необходимости отправляется Slack-уведомление.
4. Подтвержденные данные переносятся в отчетную таблицу.
5. Python-скрипт может взять список партнерских ID и обновить данные через API.
6. После API-операции скрипт повторно читает значение и проверяет результат.
7. Статус обработки записывается в таблицу или лог, чтобы успешные операции не выполнялись повторно, а ошибки можно было обработать повторно.

## Что демонстрирует кейс

- умение разобрать ручной операционный процесс и выделить повторяемые действия;
- автоматизацию работы с таблицами и статусами;
- интеграционную логику между Google Sheets, Slack и внешним API;
- обработку повторных запусков и частичных ошибок;
- базовую проверку результата после API-операции;
- техническую документацию и описание архитектуры;
- аккуратную подготовку публичной версии без чувствительных данных.

## Безопасность и публичная версия

Публичная версия репозитория не содержит:

- production credentials;
- реальных токенов и API-ключей;
- реальных spreadsheet ID;
- внутренних Slack ID;
- названий компаний;
- коммерческих данных;
- реальных данных партнеров или пользователей.

Конфигурационные значения должны храниться локально: через Script Properties в Google Apps Script, `.env`-файлы, OAuth-файлы и другие локальные настройки, которые не публикуются в репозитории.

## Ограничения проекта

Это не универсальный SaaS-продукт и не готовый фреймворк. Кейс отражает автоматизацию конкретного операционного процесса и подготовлен как портфолио-пример.

Часть интеграций нельзя запустить без доступа к исходным Google Sheets, Slack workspace и партнерской платформе. Поэтому публичная версия показывает архитектуру, код, структуру и подход к автоматизации, но не раскрывает реальные данные и доступы.

## Как этот кейс связан с моим профилем

Кейс релевантен для ролей:

- Integration Specialist;
- Affiliate TechOps;
- Implementation Specialist;
- Technical Operations Specialist;
- Application Support / Platform Support с техническим уклоном;
- System Analyst / Integration Analyst junior+ уровня;
- Payment Operations / Integration Support, где важны статусы, сверки, API, логи и разбор ошибок.

Основная ценность проекта — не в объеме кода, а в демонстрации практического подхода: взять ручной процесс, описать его логику, связать несколько систем, добавить проверки, уведомления, логи и сделать процесс более контролируемым.
